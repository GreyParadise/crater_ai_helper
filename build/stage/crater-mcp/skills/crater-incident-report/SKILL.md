# Crater 故障上报：判断 → 取证 → 上报 → 兜底

你面对的不是"匹配关键词"，而是**判断一个问题的责任归属与影响面**。上报的价值 = 让管理员少花时间定位，同时让用户能继续干活。

**两条同等重要的原则**

1. **该报的不报 = 让用户独自踩坑，其他人还会再踩一次**；
2. **不该报的乱报 = 消耗管理员注意力，真正的故障被淹掉**。

所以下面给的是**判断方法**，不是关键词表。文末有 5 个真实案例的完整判断示范。

---

## 0. 硬性要求（先看这一节）

**MUST —— 判定为平台侧问题时，你必须上报，而不是只告诉用户"失败了"。**

- 只要 `Q1 = 平台侧/平台环境`，就**必须调用 `crater_feedback_submit`**，并在回答用户时带上反馈编号；
- **禁止静默失败**：用户因平台侧原因无法完成任务，而你既没上报、也没说明为何不报，视为本次处理未完成；
- **唯一允许不上报的两种情形**：① 命中 §2 的三个否决项；② 用户明确说"不用报"。
  这两种情况都**必须在回答里写明一句理由**（例："这是镜像里缺库，属用户侧问题，未上报；处理办法是…"）；
- **上报 ≠ 完成**：必须是「上报（或说明不报的理由）+ 让用户能继续干活的兜底方案」，缺一不可；
- 中置信度（`Q4 = 中`）允许先问用户，但**问句要在同一轮里发出**并给出默认建议
  （"我倾向于报给管理员，你同意我就提交"）；用户没回应就按不上报处理，但仍要给兜底方案。

## 1. 判断框架：四个问题

按顺序问自己四个问题，前两个决定"要不要报"，后两个决定"报得多急/多细"。

### Q1 归因：这个失败边界在谁那边？

| 归属 | 判断依据 | 归属结论 |
| --- | --- | --- |
| **平台代码/配置** | 错误来自后端/网关/K8s 准入（4xx/5xx 且 `msg` 指向服务端逻辑）；平台自己生成的参数不合法（如 ingress host 用了 IP）；平台应注入的凭据/挂载缺失；平台接口不存在或被禁用；平台数据与集群实际不一致 | **平台侧** ✅ |
| **平台环境/基础设施** | 镜像仓库鉴权、存储卷、网络策略、驱动/CUDA 版本、节点状态、配额与计费开关、证书过期 | **平台侧（环境）** ✅ |
| **用户资产** | 用户自己的镜像内容（缺库、glibc 版本、Dockerfile 写错）、自己的脚本、自己的数据集内容 | 用户侧 ❌ |
| **用户操作** | 参数类型/范围错误、必填项缺失、把中文显示名当 `jobName`、账号没选对、余额/配额不足 | 用户侧 ❌ |
| **外部依赖** | 上游模型站/PyPI/公网不可达、用户私有 registry 自己的权限设置 | 看影响面，通常❌ |

> 关键技巧：**把变量换掉再试一次**就能定位归属。
> 换公共镜像还能跑 → 问题在用户镜像；换账号还报错 → 不是配额；换个作业名/节点还失败 → 不是单点；网页端同样失败 → 不只是 CLI/MCP 的问题。

### Q2 影响面：别人会不会也踩？

| 情况 | 影响面 |
| --- | --- |
| 平台某个接口整体不可用 / 某类作业全部失败 / 某节点上所有作业异常 | **全体**（必报） |
| 某个功能对所有人都缺（例如 CLI 没有上传接口） | **全体**（必报，属能力缺口） |
| 只有某个镜像/某个数据集/某个作业有问题，但根因在平台注入的配置 | **一批人**（报） |
| 只有当前用户自己的镜像、脚本、参数有问题 | **一个人**（不报，直接教他怎么改） |

**即使只有一个人受害，只要根因在平台侧（Q1 为"平台"），也要报** —— 否则下一个人还会踩。

### Q3 用户自己能不能解决？

- **能自己解决**（改参数、换镜像、换节点、换构建方式）→ 教他怎么解决，**同时**如果根因在平台侧仍要报（带 workaround）；
- **解决不了**（接口 500、平台把 host 配错、仓库鉴权平台侧错误）→ 必报，并且你要给"临时绕法"。

### Q4 置信度：你现在有多确定？

| 置信度 | 处理方式 |
| --- | --- |
| **高**（原始报错明确指向服务端 / 换变量复现 / 已排除用户侧） | 直接上报，`auto: true` |
| **中**（现象像平台问题，但你没排除用户侧） | **先用一句话问用户**："这看起来是平台侧的问题（原因 ××），要我把它整理成反馈报给管理员吗？" 得到同意再报 |
| **低**（可能只是用法不对） | 不上报，先给出正确用法；如果用户坚持或反复遇到，再走"中置信度"路径 |

> 不要因为"怕漏报"而无脑上报。**中置信度先问一句**，既不打扰管理员，也不会让用户觉得你在甩锅。

## 2. 一句话判据（快速自查）

> **"这个问题，是我（用户）自己造成的，还是平台本该做对却没做对的？如果是后者，或者我不确定但用户已经卡住了 —— 就报。"**

配套的三个否决项（命中任一条就不报）：

1. 换掉用户侧变量（镜像/参数/账号/作业名）后问题消失；
2. 报错信息明确指向用户输入（400/422、`invalid value`、`record not found`、`insufficient quota`）；
3. 已知过渡态：新注册 60 秒内文件系统 `403 unauthenticated`；作业刚提交 10 秒内的 `Pending`。

---

## 3. 类型归属（category 怎么选）

| 情况 | category |
| --- | --- |
| 平台本该做对却没做对（报错、崩溃、配置错误、数据不一致、接口不可用） | `bug` |
| 平台能力缺失 / 体验不合理（"CLI 没有上传接口""希望支持按节点筛选"） | `feature` |
| 现象可疑但你没定性（凭据、缺失文档、行为是否符合预期） | `question`（并在标题写"疑似"） |

`feature` 也算有效上报 —— **能力缺口不报，管理员永远不知道大家都在绕路**。

---

## 4. 上报前必做

1. **换变量复现一次**（Q1 的技巧），把结论写进正文；
2. **查重**：`crater_feedback_mine({ onlyUnresolved: true })` —— 已有同类未处理反馈就别再报，回答用户时说明"已上报（#编号），处理中"；
3. **一条会话里踩了多个问题 → 合并成 1 条**（bug 与 feature 分开最多 2 条），在正文里用 ①②③ 列清楚，不要一件事报一次。

---

## 5. 取证与提交（怎么调用这一个工具）


- 工具/命令名（`crater_jobs_create_jupyter`、`crater file upload`）
- **原始英文报错**，原样保留（HTTP 状态码、业务 code、K8s 报错串）
- 对象标识：`jobName`（不是中文显示名）、镜像完整地址、文件逻辑路径、账号名、节点名
- 发生时间 + 时区
- 你做过的**变量替换实验**与结果（这是最有价值的部分）
- 对用户的影响 + 你给的 workaround
- 期望行为

**绝不填写**：密码、token、JWT、cookie、私钥（工具侧会脱敏，但不要主动写）。

### 5.1 标准调用模板（照抄改内容即可）

```json
{
  "tool": "crater_feedback_submit",
  "arguments": {
    "category": "bug",
    "auto": true,
    "impact": "all",
    "confidence": "high",
    "title": "Jupyter 作业创建时 ingress host 被填成 IP，K8s 拒绝",
    "content": "触发：crater_jobs_create_jupyter(name=demo)\n报错原文：Ingress ... is invalid: spec.rules[0].host: Invalid value ...\n变量替换：换作业名/换账号均复现 → 与用户输入无关\n时间：2026-11-09 10:00 (UTC+8)\n影响：所有 Jupyter 作业无法创建\n期望：host 为 IP 时退化为按路径路由",
    "pageUrl": "/portal/jobs/new"
  }
}
```

字段速查：

| 字段 | 必填 | 取值与说明 |
| --- | --- | --- |
| `category` | ✅ | `bug` 平台缺陷 / `feature` 能力缺口 / `question` 疑似未定性 / `other` |
| `title` | ✅ | ≤110 字，"哪里 + 什么现象"，禁止"出错了"这类无法定位的标题 |
| `content` | ✅ | 按 §5 清单写；多条问题用 ①②③ 编号分段 |
| `auto` | ✅（agent 自动上报时） | 固定 `true`，工具会给标题加 `[Agent 自动汇报]` 前缀，管理员靠它区分机器报的 |
| `impact` | 建议 | `all` 全体 / `some` 一批人 / `one` 仅当前用户（根因仍在平台侧时）→ 工具写入正文首行供分诊 |
| `confidence` | 建议 | `high` / `medium` → 同样写入正文首行 |
| `pageUrl` | 可选 | 相关页面路径，如 `/portal/jobs/detail` |
| `contact` | 可选 | 一般不要填（用户账号已能定位到人） |

### 5.2 返回值怎么处理

| 返回 | 你要做的 |
| --- | --- |
| `{ submitted: true, id: 12 }` | 在回答里写明"已上报，反馈 **#12**"，并继续给兜底方案 |
| `{ skipped: true, reason: "30 分钟内已报过…" }` | **不要换标题重报**；说明"该问题已上报过（处理中）"，转去给兜底方案 |
| `{ skipped: true, reason: "本小时已达上限…" }` | 把多个问题合并成一条再报；仍不行就说明并同时贴给用户手动提交 |

### 5.3 上报通道不可用时

- 工具不存在 / 该实例未开启 `feedback` 组 / 返回 403 →
  明确告诉用户"上报通道未启用"，并把按 §5 整理好的**证据原文**贴给用户，
  让他手动提交到「更多 → 问题反馈」（不要因此就不整理证据）。

## 6. 五个真实案例的判断示范

下面是某次真实会话中 agent 遇到的问题清单。**注意它们的归属各不相同**：

| 现象 | Q1 归因 | Q2 影响面 | 判断 | 上报怎么写 | 事后核实（管理员排查结论） |
| --- | --- | --- | --- | --- | --- |
| `crater file upload` 返回 **404**（后端没有上传接口），只能用环境变量分块传 | **平台**（能力缺口） | 全体 CLI 用户 | ✅ **报**（`feature`） | "CLI `file upload` 请求的后端接口返回 404，实际无该接口；目前只能通过作业环境变量分块传输。影响：CLI 无法按文档上传文件。期望：补齐接口或文档标注不可用" | **真缺陷（部署）**：线上 storage-server 用的是上游预编译镜像，缺 `POST /api/ss/upload/*path` 路由 → 已换成自建镜像修复。判断正确：这确实是平台侧、会影响全体 CLI 用户 |
| 私有 Harbor 项目镜像**拉不到，401** | **需再判断**：若平台应注入 imagePullSecret 而没注入 → 平台；若用户自己没配 registry 凭据 → 用户 | 平台侧=一批人 / 用户侧=一个 | ⚠️ **先验证**：同账号拉公共镜像是否正常？同 registry 的其他镜像能否拉？错误是 registry 拒绝（`401 unauthorized`）还是 K8s 拉取失败（`ErrImagePull`）？**平台注入缺失就报，用户凭据问题就教他配** | 平台侧：附 `kubectl describe pod` 的 `Failed to pull image` 原文 + 该账号其他镜像是否同样失败 | **真缺陷（配置）**：Harbor 拉取机器人 `robot$crater-pull-all` 的项目权限里没有该用户 → 补权限后实测 pull 成功。判断正确：**先验证再定性**是对的，这条如果直接说"用户自己没配凭据"就错了 |
| Jupyter 作业创建失败：**ingress host 配成了 IP**，K8s 拒绝 | **平台**（平台自己生成了非法参数） | 全体（任何名字里带点的作业都会踩） | ✅ **报**（`bug`，高置信） | "创建 Jupyter 作业时平台用 `<username>`/IP 生成 ingress host，K8s 拒绝：`Ingress is invalid: spec.rules[0].host: Invalid value`。复现：`crater_jobs_create_jupyter` + 任意作业名（无 hostname 配置）；变量替换：换作业名、换账号均复现" | **真缺陷（代码）**：`config.host=172.16.16.140`（IP）被直接写进 `spec.rules[0].host` → 已改为 IP/空 host 退化成按路径路由。判断正确：高置信、直接报 |
| SSH 与端口转发**入口不稳定，多数请求到不了任务内部** | **平台**（网络/入口） | 全体 | ✅ **报**（`bug`） | 附：失败比例、错误形态（超时/connection refused/502）、目标端口、是否特定节点、是否与 ingress/nodeport 有关 | **部分可改进**：入口本身可达，但 NodePort 随作业重建变化、路径入口要求严格尾斜杠 → 属"体验缺陷"而非"完全不可用"。教训：报之前**先量化失败比例与具体形态**，否则会被判定为"用户不会用" |
| `python:3.11-slim` 的 **glibc 拒绝加载要求可执行栈的库**，TensorRT 构建器起不来 | **用户侧**（用户选的镜像基础库限制），但 **平台侧可改善**（文档/推荐镜像/编译参数） | 一个（写 TensorRT 的人都会踩） | ❌ **不报为 bug**；✅ 作为 `feature`（低优先）可选上报"建议在文档/镜像模板里说明需 `noexecstack` 的依赖场景" | 直接教用户：换 `-devel`/更高 glibc 的镜像、`patchelf --clear-execstack`、或链接时加 `-Wl,-z,noexecstack` | **与平台无关**：容器基础镜像 + TensorRT 库的 `execstack` 问题 → 给用户侧解法即可。判断正确：没把用户环境问题甩给管理员 |

**从这 5 条能看出什么**

- 判断的核心不是"报错长什么样"，而是 **谁本该做对**；
- 同一个"失败"，可能是平台 bug（③）、平台能力缺口（①）、平台配置（②）、平台不稳定（④）、用户环境（⑤）；
- 遇到 ② 这种"可能是平台也可能是用户"的，**先去验证，别猜**；验证不了就归到"中置信度"→ 先问用户；
- 一次会话踩到 5 个问题 → **合并成 1 条**（bug ①②③④）+ 1 条 feature（⑤ 的建议），正文用 ①②③④ 编号，每条一段。

合并后的范本：

```json
{
  "category": "bug",
  "auto": true,
  "title": "CLI/作业链路上 4 处平台侧问题（上传接口缺失 / ingress host 非法 / 端口转发不稳 / 私有镜像拉取失败）",
  "content": "本次会话以一个普通用户跑通「建作业 → 传文件 → 用自建镜像」时，命中 4 个平台侧问题：\n\n① CLI 文件上传接口不存在\n操作：crater file upload ...\n报错：HTTP 404（该后端路径无对应 handler）\n影响：文档描述的 CLI 上传能力实际不可用；退化为作业内环境变量分块传输\n\n② Jupyter 作业创建失败（平台生成非法 ingress host）\n操作：crater_jobs_create_jupyter(name=...)\n报错原文：Ingress ... is invalid: spec.rules[0].host: Invalid value ...（host 被填成 IP）\n复现：换作业名/换账号均复现；变量替换确认与用户输入无关\n\n③ SSH / 端口转发入口不稳定\n现象：约 70% 连接超时或 connection refused，偶发成功；跨节点一致\n影响：无法稳定进入任务内部调试\n\n④ 私有 Harbor 项目镜像拉取 401\n报错原文：Failed to pull image \"<registry>/<repo>:<tag>\": ... 401 unauthorized\n已排查：同账号拉公共镜像正常；该 registry 其他公开镜像正常 → 指向私有项目的 imagePullSecret/凭据注入\n\n时间：2026-11-09 10:00 (UTC+8)，账号 q-x，节点 gpu004\n期望：①②③ 为平台缺陷需修复；④ 若凭据应由平台注入请补齐，否则请在文档说明用户需自配 registry 凭据",
  "pageUrl": "/portal/jobs/new"
}
```

## 7. 上报之后（别只报不干）

1. **告诉用户编号**：例如"已整理成反馈 #12 报给管理员，可在「更多 → 问题反馈」看进展"；
2. **给出可用绕法**，让用户今天就能干活：日志看不了 → `crater_jobs_detail` 的 `podGroupPhase`/事件 → 或 WebIDE 里 `tail -f`；构建失败 → 换 `kaniko`/`dockerfile` 构建；接口 500 → 换等价工具或换账号；节点异常 → `crater_resources_*` 找可用节点；上传受限 → 作业内分块传输；私有镜像 → 先推到公共项目或用平台可拉取的镜像；
3. 用户再问起时，先 `crater_feedback_mine` 看管理员回复并**转述**；
4. 管理员要求在补充信息时，用新反馈说明"补充 #12"，不要重复原问题。

## 8. 反例

| ❌ | ✅ |
| --- | --- |
| 标题"出错了" | "Jupyter 作业创建时平台把 ingress host 填成 IP，K8s 拒绝" |
| 正文"作业跑不起来" | 报错原文 + jobName + 变量替换结论 + 影响 + 期望 |
| 参数写错也上报 | 直接告诉用户改 `jobName` |
| 一次会话报 5 条 | 合并成 1 条 bug + 1 条 feature |
| 报完就完了 | 编号 + workaround + 后续跟踪 |
| 凭据/密码写进正文 | 只写"凭据注入疑似缺失"，不贴任何凭据 |

# Crater 故障自动上报

你的职责：**遇到平台故障不要只是"告诉用户失败了"，而是把证据整理好、自动报给管理员，并让用户能继续干活。**

---

## 1. 先判断：这算不算平台故障？

用下面三分类，**只有 A 类才上报**：

| 类别 | 典型信号 | 处理 |
| --- | --- | --- |
| **A. 平台故障（上报）** | 接口返回 **5xx / 502 / 503 / 504**；网关或后端报 `Internal Server Error`；请求**超时**且重试 2 次仍失败；作业长时间 `Pending` 而节点有空闲、配额也够；作业 `Running` 但**没有日志输出**、pod 反复重启（`CrashLoopBackOff` 属于用户镜像问题，`ImagePullBackOff` 才是平台/镜像库问题需判断）；镜像构建在**构建器内部**异常失败（不是 Dockerfile 写错）；`/api/ss/*` 返回 **403 `unauthenticated`** 而账号确实存在（注意：新注册 1 分钟内属正常开通期，见下）；接口返回的数据与 `kubectl`/平台页面明显矛盾；**同一操作稳定复现失败**且错误来自服务端 | 上报 + 给出绕过方案 |
| **B. 用户/参数问题（不上报）** | 400/422 参数校验失败；`record not found` 因为传了中文显示名而非 `jobName`；配额不足、余额不足；无权限（明确是"你只能访问自己的记录"）；镜像地址写错；Dockerfile 语法错误；YAML 语法错误 | 直接告诉用户怎么改，**不要浪费管理员时间** |
| **C. 已知过渡态（不上报）** | 新注册用户在 **60 秒内**访问文件系统得到 `403 unauthenticated`（账号同步有 1 分钟窗口）；作业刚提交 10 秒内的 `Pending` | 告诉用户等一会儿再试 |

判断顺序：**先自己重试一次**（换等价调用、去掉可选参数），仍失败再定性。不要一上来就报。

---

## 2. 上报前必须做的事

1. **重试一次**，确认不是瞬时抖动；
2. **查是否已经报过**：调 `crater_feedback_mine`，`onlyUnresolved: true`
   - 若已有同类未处理反馈 → **不要再报**，在回答用户时说明"该问题已上报（#编号），管理员处理中"；
3. **收集证据**（这是上报质量的关键），至少包含：
   - 触发操作 + 工具名（如 `crater_jobs_logs`）
   - 报错原文（HTTP 状态码 / 业务 code / 关键错误串，**保留原始英文错误**，便于管理员 grep 日志）
   - 涉及对象：`jobName`（**不是中文显示名**）、镜像地址、文件逻辑路径、账号名
   - 发生时间（本地时间 + 时区）
   - 已做过的排查（"重试 2 次""换账号无变化""同节点其他作业正常"）
   - 期望行为

---

## 3. 提交

调用 `crater_feedback_submit`，参数要点：

```json
{
  "category": "bug",
  "auto": true,
  "title": "作业日志接口对 Running 作业返回 500",
  "content": "触发操作：crater_jobs_logs(jobName=vsc-fulong-261109-a1b2c)\n报错原文：HTTP 500 {\"code\":50001,\"msg\":\"failed to get pod logs: container not started\"}\n发生时间：2026-11-09 10:12 (UTC+8)\n已排查：重试 2 次均失败；同节点 gpu004 上另一个作业可正常取日志；网页端同作业也是空白\n影响：无法查看训练日志，作业仍在运行\n期望：Running 状态的作业能返回日志，或至少返回明确的容器状态",
  "pageUrl": "/portal/jobs/detail"
}
```

**硬性规则**

- `category` 用 `bug`（平台故障）；功能缺失用 `feature`，别混用；
- `auto: true` —— 由你自动上报时必须带上，管理员靠 `[Agent 自动汇报]` 前缀区分；
- `title` ≤ 110 字，一句话说"哪里 + 什么现象"，**不要写"出错了"这种无法定位的标题**；
- `content` 必须含**报错原文**与**对象标识**；只写"失败了"的上报等于没报；
- **绝不能**把密码、token、JWT、cookie、私钥写进 `content`（工具侧会脱敏，但你不要主动填）；
- 同一故障 **30 分钟内只报一次**、每小时最多 **6** 条 —— 工具会拦，别绕过去反复试。

工具会返回 `{ submitted: true, id: 12, ... }` 或 `{ skipped: true, reason: "..." }`；被 skip 时**不要换标题再报**，按 reason 的提示处理。

## 4. 上报之后（重要，别只报不干）

1. **把反馈编号告诉用户**：例如"已上报给管理员（反馈 #12），处理进展可以在「更多 → 问题反馈」查看"；
2. **给出替代方案/绕过路径**，让用户能继续工作，例如：
   - 日志拉不到 → 用 `crater_jobs_detail` 看 `podGroupPhase` / 事件；或建议在 WebIDE 里 `tail -f`
   - 镜像构建失败 → 换 `image build dockerfile` / `kaniko` 另一种构建方式
   - 某接口 500 → 换等价工具（列表类可用 `facets` 或 WebIDE 内自查）
   - 节点/资源异常 → 用 `crater_resources_*` 找可用节点后重试
3. 下次会话或用户再问起时，先查 `crater_feedback_mine` 看管理员是否已回复，**把回复转述给用户**；
4. 如果管理员回复要求补充信息（如具体时间、pod 名），按要求补充——**用新的反馈**说明是"补充 #12"，而不是重复原问题。

---

## 5. 反例（会被管理员骂的报法）

| ❌ 不要这样 | ✅ 应该这样 |
| --- | --- |
| 标题"出错了" | "镜像构建接口对 kaniko 类型返回 500" |
| 正文"作业跑不起来" | "WebIDE 作业 vsc-x-261109-a1b2c 卡 Pending 12 分钟；节点 gpu004 空闲 2 卡；配额充足；事件显示 `FailedScheduling: 0/4 nodes available`" |
| 参数写错也上报 | 那是 B 类，直接告诉用户改 `jobName` |
| 一口气报 5 条同类问题 | 合并成 1 条，列出 5 个受影响对象 |
| 把报错截图/口述转成中文丢了原文 | 保留原始英文错误串（管理员要拿去 grep 日志） |
| 报完就完了 | 报完给绕过方案 + 编号 |

---

## 6. 与其它 skill 的关系

- 工具怎么选、参数怎么填 → 见 `crater-mcp-ops`；
- 本 skill 只负责**故障定性 + 上报 + 兜底**，不改变工具调用方式；
- 如果 `crater_feedback_submit` 本身不可用（未注册或返回 403），说明该 MCP 实例没有开启 `feedback` 工具组
  → 明确告诉用户："上报通道未启用，请把上述信息手动提交到「更多 → 问题反馈」，或联系管理员。"
